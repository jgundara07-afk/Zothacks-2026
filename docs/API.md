# OneThing app API
All requests and responses are JSON except PDF uploads. Vite proxies `/api/...` to Flask. Every route except `GET /health` requires `Authorization: Bearer <Supabase access token>`. Flask verifies the token with Supabase Auth and scopes private records to that user ID. Errors use `{ "error": "Readable message" }` and appropriate HTTP status codes, including 401/403/503.

## Default collected mode
`ONETHING_DATA_MODE=catalog` reads the bundled, checksum-validated `backend/catalog/opportunities.json.gz`. It does not contact providers or overwrite profile/activity storage. Missing or corrupt files fail startup instead of silently substituting samples. Restart Flask after a manual export. Set `ONETHING_DATA_MODE=sample` for the explicit fictional fixture; that mode retains the original unpaginated feed contract for regression/demo use.

- `GET /health`: `{status, storage, data_mode, catalog_records}`.
- `GET /opportunities`: `{profile, checkin, opportunities, quests, total, offset, limit, has_more, data_mode, kinds}`. Default page size 40, maximum 100. Filtering happens before pagination. Each card includes a stable collected ID, `sample:false`, source URL/provider, collection time, availability, original source facts and personalization estimates. `saved`, `matching_tags`, and a matching `suggested_quest_id` are added for the app. The page embeds its quests so details and filters use the same records.

Feed filters: any selected interest, goal, or skill can match within its group (OR). Difficulty, time, type, and metadata choices are alternatives within their groups; all groups are combined with AND. Near me always imposes the radius constraint, even alongside another location choice. Broad personal-growth fallback tags do not qualify as supported interest matches.

| Parameter | Meaning |
| --- | --- |
| `interests`, `goals` | Exact UI labels in `shared/preferences.json`; at most ten interests and three goals. `Internship` maps to the catalog software-internship goal. |
| `challenges`, `time` | Match `personalization.challenge_levels` and `personalization.time_buckets` of the full opportunity. Preparation step size remains independent. |
| `locations` | Online / Remote, On campus, In-person events, Near me. |
| `commitment` | Full opportunity commitment; A mix of both accepts either. |
| `step_size` | Any, Small, Medium, Big; selects a preparation variant. |
| `kind`, `skills` | Repeated source opportunity types or skill labels. |
| `q` | Space-separated text terms in title/description/organization/location. |
| `lat`, `lon`, `radius_km` | Near me requires finite coordinates. Default radius 25 km; maximum 500. Unknown source coordinates are excluded. |
| `offset`, `limit` | Nonnegative offset; limit 1-100. |
| `source` | Repeated exact provider IDs. Unknown types, skills, providers, and metadata values return 400. |
| `experience`, `cost`, `prerequisites`, `duration_quality`, `schedule` | Repeated exact values from `/catalog/options.filter_options` (shared/catalog_filters.json). Unknown facts match only the explicit Unknown choice. Experience is an editorial estimate, not eligibility verification. None stated means an explicit source statement; missing prerequisite information is Unknown. |
| `max_minutes` | Positive finite cap on the full duration range upper bound. Unknown totals are excluded. |

Normal time buckets are disjoint: under 5, [5,15), [15,30), [30,60), [60,180), and 180+ minutes. They describe the full opportunity, using source durations or labeled planning estimates. Full opportunity duration and inferred/source facts stay in `personalization.duration`. Multi-day is a planning category for the larger opportunity. Near me comes from distance to approximate City GIS points, not a claim about a trailhead or accessibility. The browser asks for location only when selected; denied access requires choosing another location or allowing access.

Past source events are excluded from discovery using export status and parseable source end dates at request time. Unknown availability remains explicitly unverified. Schools, providers and employers determine eligibility, deadlines and access; read the original source.

## Profiles and daily pace

### Achievement atlas
The `achievements` field on `GET /progress` now contains 94 implemented achievements: the original ten and 84 additional mountain achievements in ten regions. Each record includes stable `id`, `number`, `region`, criteria, flavor, threshold, current progress and permanent unlock time. The Progress map derives exploration solely from `unlocked`, never from points. Unsupported requested achievements are omitted: Mount Syllabus (no classes in the live catalog), Mount Simulator (no job simulations), Mount Keyword and Mount Gap Bridger (no resume analyzer), and Mount Polymath (only eight skill tags are currently available). Definitions for the new mountains live in `backend/achievement_catalog.json`.

`POST /saved` optionally accepts `filters:{active:boolean,challenges:string[]}`. New saves preserve timestamps, source type and discovery context; successful save/unsave transitions append bookmark history. Retries do not duplicate history. Unknown legacy save dates are never invented. Goal changes after initial profile setup append an activity record.

`GET /achievement-options` returns supported self-reported outcome values/labels. `POST /completions` optionally accepts `actual_minutes` (integer 1–1440, omitted if not tracked) and `outcomes` (up to three supported labels). These are explicit user reports, not provider verification. Estimated quest durations never count as logged effort. Applications, attendance and certification outcomes require compatible opportunity types; preparation completion alone does not qualify. Completion retries preserve the original work log and never add rewards or badge credit twice. The app no longer shows a time/outcome form; it sends only `{quest_id}`. A quest may instead declare `outcomes` that its single goal self-reports (for example `Submit the application` → `applied`, `Go to the event` → `event_attended`, `Finish the course` → `certification_completed`, the authored Pomodoro task → `focused_pomodoro`); completing it records them.

`POST /recap/narrative` also supports `{period:"year",year:"2026"}` (2000–2100), with Pacific-calendar year boundaries. Successful local and Gemini recaps return `recap_id`, up to five `highlights` (title/date, ranked by recorded quest points then time), and refreshed badges. Recap generation itself awards generation achievements, not view/share achievements. Gemini archetype changes require real Gemini responses in adjacent monthly recaps.

`POST /activity/events` accepts `{event,recap_id?}` for `analytics_view`, `skills_view`, `fallback_read`, `highlight_view`, and `share_click`. The frontend records views when the relevant content enters the viewport. Recap events require an existing recap; fallback views require a local source, and highlight/share events require nonempty recorded highlights. Events are idempotent per recap, or per Pacific day for analytics, and return updated achievements. Clicking Share opens the browser share dialog or copies text; the app never sends messages automatically.

Recap choices: `POST /recap/narrative` accepts `{period:"lifetime"}` (default) or `{period:"month",month:"YYYY-MM"}`. Monthly boundaries use Pacific calendar days with an exclusive next-month end; Gemini receives every completion only inside that period. Responses include `period`, `start`, `end`, `badges` and eight narrative fields including `signature_move` and `plot_twist`. Empty periods skip Gemini. Invalid periods/months return 400.

`GET /progress` includes ten `achievements`, each with `id`, `name`, `criteria`, `flavor`, `progress`, `target`, `unlocked`, and `earned_at`. Unlocks persist in activity and cannot be revoked by unsaving items. A daily micro-goal is a daily quest of at most five minutes; the 7-day badge requires consecutive Pacific days with one such completion. Resume/LinkedIn, wellness/ergonomics and networking badges use recorded task metadata, with source lookup for legacy activity. Distinct authored task categories count separately from external opportunity types. Kindred Peak (the `warm-intro` badge) requires three distinct networking/community opportunities, so repeating preparation for one event does not count as three events. Backlog means saved opportunities with no completed quest; it unlocks at ten. Recap badges add `earned_in_period`; the gallery is a lifetime collection with new-in-month highlights. Completion retries never increase badge counters.
- `POST /profiles`: `{goals: string[], interests: string[], skills: string[], preferences:{challenges:[],time:[],locations:[],commitment}}` returns `{profile}`. Up to ten supported interests and three supported goals; excess selections return HTTP 400. Legacy singular `goal` and legacy interest tags remain accepted. Updates do not reset activity. Internship labels normalize on load/save. Interest selection stops at ten and goal selection at three; stored selections are restored up to their respective limits. All choice groups may be empty; existing skill validation still requires a nonempty skill list.
- `GET /checkins`: `{checkin, date, timezone}`.
- `POST /checkins`: `{mood:"Low"|"Okay"|"Good",effort:"small"|"medium"|"big"}`. One updatable Pacific-day check-in, requires a profile. A check-in alone earns no points. With no explicit size/time/challenge filter the daily effort is a preference for selecting a quest.

## Saves, quests and rewards
- `POST /saved` / `DELETE /saved`: `{opportunity_id}` returns `{saved, opportunity_id}`. Requires a profile; unknown IDs return 404. Save and unsave are idempotent. Existing sample IDs in persistent storage remain resolvable, but are never mixed into collected discovery.
- `GET /saved`: `{opportunities, quests}` for all bookmarks, independent of current discovery filters and date. Allows viewing a saved event after it ends; its source metadata remains visible.
- `GET /quests`: `{quests}` for saved opportunities in collected mode. Repeat `opportunity_id` to request up to 100 specific opportunities. Sample mode without IDs retains all fixture quests.
- Each collected quest has a deterministic ID (`<opportunity-id>::small|medium|big|hard|challenging|project`), `opportunity_id`, title, description, checklist `steps`, minutes, exact `time_bucket`, difficulty, size, effort, server-defined points, `daily:true`, `estimated:true`, `quest_type:"preparation"`, and `completed` for today. Generated actions cover source review, planning and preparation deliverables. They never imply completion of a source opportunity, enrollment, application, visit or physical route.
- `POST /completions`: `{quest_id}` returns `{already_completed, points_earned, progress}`. Requires a profile and saved opportunity. Rewards are calculated by the server; retries award zero extra points. Helper quests (`quest_type: "helper"`, `daily: false`) earn once each. Daily quests (authored tasks, outing quests) can earn once per quest per Pacific day. Legacy fixture quests keep their once-only/daily behavior.
- `GET /progress`: points, saved/completed counts, completed IDs, activity, current/best streak, `active_today`, `today`, timezone. One or more completions on a Pacific calendar day count as one streak day.
- `GET /analytics`: progress, category/skill/difficulty counts, estimated preparation minutes, seven-day activity, top category/skill. Reads the same collected opportunity and quest IDs as the completion routes; totals reflect recorded activity, not browsing.
- `POST /recap/narrative`: `{narrative, source, activity_count}` for the designed Wrapped-style recap. With completed activity, Gemini receives aggregate progress plus every recorded completion, including date, title, category, skills and difficulty, so the story can reflect month- and year-long patterns. Profile fields and location are not sent. The server validates and bounds the structured response, then uses a local recap if Gemini is unavailable or returns invalid output. With no completions, it returns a local first-step story without calling Gemini. `narrative` has `archetype`, `evidence`, `description`, `quest_line`, `signature_move`, `rhythm_line`, `plot_twist`, `onething_line` and `next_step`, one per story slide. The response also includes `stats`, computed only from recorded completions in the period, which drive each slide's headline and visual: `completed_count`, `points`, `minutes` (estimated), `active_days`, `best_streak`, `top_category`, `top_category_count`, `category_count`, `categories` and `top_skills` (`[name, count]` pairs), `weekday_counts` (Monday first), `busiest_weekday`, `busiest_weekday_count`, `busiest_day` (`{date,count}`), `first_quest`, `latest_quest` and `toughest_quest` (`{title,date,difficulty,category}`), `difficulties`, `badges_earned` and `latest_badge`. Configure `GEMINI_API_KEY` in the ignored root `.env`; `GEMINI_MODEL` defaults to `gemini-3.8-flash`.

Profiles and activity use MongoDB when configured or local SQLite otherwise. Atomic unique activity IDs protect rewards. The catalog file is immutable during browsing; saves/completions live in the separate store. Existing progress and bookmarks survive mode switches and restarts.

## Resume suggestions
- `POST /resume-analysis`: `{text,role}`. Text must contain 1-30,000 nonblank characters; roles are Software developer, Product designer, Community organizer.
- `POST /resume-analysis/pdf`: multipart `file` and `role`. Maximum 5 MB, 20 pages, 30,000 extracted characters, 2 MB uncompressed page stream. No OCR; protected/corrupt/scanned PDFs return a clear error.
- Returns `{role,found_skills,gaps,recommendations,method}`. Suggestions reference up to 100 matching, nonexpired collected opportunities in default mode. This is local keyword matching against fictional role templates; missing words are exploration prompts, not assessed skill deficits. Raw resume text/files are neither stored nor sent to external AI.

The lower-level read-only `/catalog/options` and `/catalog/opportunities` API preserves the canonical data taxonomy and explicit full/first/micro-step scopes; see [CATALOG_API.md](CATALOG_API.md).

### Demo clock and ranged analytics
`POST /demo/clock` accepts `{ "date": "2026-10-18" }` or `{ "reset": true }`. Persisted Pacific date affects completion timestamps and daily quest eligibility; source availability uses real time. Disabled with `ONETHING_DEMO_TOOLS=0` (403). `/progress` includes `demo_clock` metadata.

`GET /analytics?period=day|week|month|year&date=YYYY-MM-DD` returns scoped `completed_count`, `points`, category/skill/difficulty counters and `series` bins, plus inclusive `start` and exclusive `end`. Weeks begin Monday; all boundaries use Pacific time. With no period, lifetime recap counters remain available.

Monthly analytics series has one bin per calendar day. The UI offers Weekly, Monthly, and Yearly views; the API still supports hourly day queries.

### Complete Progress handoff
`GET /progress/data?date=YYYY-MM-DD` is a read-only versioned payload containing lifetime `progress`, `climb`, calendar active-day counts, `analytics` for week/month/year, and lifetime `recap`. The optional date controls analytics only. See `data/README.md` for field mappings and `data/progress.json` for a persisted demo snapshot. Refresh the file using `python backend/export_progress.py` from an environment with the backend requirements installed. Live completions remain stored in the configured MongoDB/SQLite store; the JSON snapshot is not a replacement database.

## Effort assessment v2
Every collected card includes `personalization.assessment`: evidence-based difficulty, estimated experience level, prerequisite status/basis, source-backed cost (Free/Paid/Unknown), duration quality, schedule type, languages, and eligibility text/verification flag. Unknown costs and eligibility are not fabricated. Difficulty describes the source activity, independently of preparation quests or duration. Lazy means a guided low-barrier activity or passive attendance, Easy means introductory practice, Medium means applied/intermediate work, Hard means advanced independent work, and Challenging means graduate/research/complex specialist material. Counts are reported honestly rather than forced into equal bins. The assistant-authored rubric processes each record; explicitly reviewed exceptions are in editorial_overrides.json. This is not a claim of individual manual review of every listing.

`personalization.duration` now includes `min_minutes`, `max_minutes`, `minutes` (only when exact bounds agree), `quality`, `scope`, and `basis`. Provider weekly ranges are multiplied only when a week count is supplied; unsupported/missing workload becomes a labeled planning range or Unknown. Class/job/internship totals remain Unknown/Multi-day rather than invented hours. Range upper bounds drive time filtering, so a 1?3 hour estimate does not pass a 60-minute cap. Map segments do not establish a whole hike duration. Source-reported event elapsed time can include breaks and overnight time.

## Discovery matching and ranking
Repeated interests, goals and skills now use OR within each group. Selected groups still combine with AND, alongside the time, difficulty, metadata, type and geographic constraints. Unsupported fallback topics remain excluded from interest matches. Results are ranked before pagination by the number of relevant selected tags (or profile tags when no explicit choices are supplied). A deterministic bonus of at most 0.25 points favors less repeated normalized titles, providers and opportunity types among eligible results. One additional relevance match is worth 1 point, so uniqueness cannot outweigh it. `ranking` exposes `relevance_score` and `uniqueness_bonus` on collected cards. The lower-level catalog API uses explicit query tags for relevance. No records are removed, and full-set scoring keeps offset pagination stable.

## Neutral discovery fallback
Only the core `GET /opportunities` discovery feed automatically offers alternatives when the entire available result set has no matches and interests or goals were selected. It relaxes interests/goals only, choosing real parks and online courses whose titles explicitly support general wellbeing or personal development. Availability, time, challenge, location/radius, skills, cost, experience, prerequisites, schedule, type, provider, text and step-size constraints still apply. Expired/cancelled records are never used. If no neutral record meets those constraints, results remain empty.

Responses include `fallback: {active, reason, relaxed_filters, message}`; active fallback cards have `recommendation_type: "neutral"`, empty `matching_tags`, and relevance score zero. The UI labels them as alternatives in onboarding/discovery/details. Matched results always take precedence. Fallback is selected before pagination, so an offset beyond a matching result set does not introduce unrelated records. Saved items and preparation quests continue using real source IDs. Lower-level `/catalog/opportunities` searches remain exact queries without automatic neutral fallback. When no personalized result exists, the first `/opportunities` page may also include `fallback.recommendation`: a self-guided next step generated by Gemini from the selected filters only. Configure `GEMINI_API_KEY` in the ignored root `.env`; `GEMINI_MODEL` defaults to `gemini-3.8-flash`. The server never sends location coordinates, and missing keys, timeouts or provider errors leave the normal fallback in place. Generated text is labeled and never presented as a live listing.

### Related onboarding suggestions
`GET /recommendations?step_size=Any&offset=0&limit=40` provides broader ranked suggestions using saved profile interests, interest categories, goals, and skills. Exact interest matches rank first; records include an honest `recommendation_reason`. `recommendation_mode: true` identifies broadened results. Onboarding uses this only when its strict search returns no records; selected preferences stay saved. The main `/opportunities` route retains its OR matching and neutral fallback. If no topical match exists, suggestions are explicitly exploratory rather than claimed matches.


## Authored general tasks

The bundled catalog includes 60 self-guided OneThing activities from `opportunity_data/general_tasks.json`. They are authored app content, not live external opportunities. Each has explicit action steps and a real completion quest.

New goals are connected to both `/opportunities` and `/catalog/opportunities` through conservative title-based classifications in `backend/goal_matching.py`. Returned `personalization.goals` includes these tags; `personalization.inferred_goal_matches` records the matched title text. These are app inferences, not provider claims. Catalog options include the new goals without modifying the immutable source export. Other filters continue to apply.

### Filter relevance improvements
- Choices within each group use OR; groups combine with AND. Location choices now follow the same rule: Near me **or** Online works as a union. Near me alone still requires coordinates and respects radius. Unknown distances are never treated as nearby.
- `q` matches every normalized query term across title, description, provider, and location. Accent and common hyphen variants are normalized; terms match word prefixes, while one- or two-character searches require whole tokens. Title evidence ranks above incidental description matches.
- Both catalog APIs return `match_details` with matched interests, goals, skills, title terms, and relevance score. Score weights are 4 per interest, 3 per goal, 1 per skill, 6 per title term, plus 4 for the complete query appearing in the title. The existing diversity bonus remains at most 0.25, so it cannot override a stronger match.
- Discovery still labels neutral/sprinkled general tasks honestly and keeps stable pagination. Core feed returns `matched_count` excluding general-task suggestions. The broader `/recommendations` route relaxes only interest/goal constraints; it now accepts and preserves the other feed filters, including time, location, difficulty, cost, and search.
- Normalized text is cached in memory with bounded caches; completion and save state are never cached by this optimization.

### Matching mode, sorting, and personal visibility
Core `/opportunities` and `/recommendations` accept:
- `match_mode=any|all` (default `any`): match any or every selected **interest**, and any or every selected **goal**. Different groups still combine with AND; time, location, challenge, and other hard constraints retain their semantics. `/catalog/opportunities` also supports this option.
- `sort=relevance|shortest|points` (default `relevance`): shortest sorts by the suggested preparation quest's minutes, points sorts descending by that quest's server-calculated reward. These refer to first steps, not full opportunity duration. Sorting happens over the full result set before pagination with deterministic tie breaks.
- `hide_saved=true|false` (default false) excludes saved opportunities. Completed work never returns to the feed: an opportunity with any completed quest is excluded, except a project, which stays until all of its helper quests are complete and whose `suggested_quest_id` is its next unfinished step. `hide_completed` is still accepted for compatibility and has no further effect. Nothing is deleted; completed opportunities stay in Saved.
- Projects: jobs/internships (6 steps: read the listing, refresh your resume, tailor it, prepare materials, submit, prep for the interview), online courses (5) and events (4) return ordered helper quests from `quests`, each with `project: {step, total}`, one goal in `steps`, its own points, and `daily: false`. Four authored "draft it" tasks (8, 12, 14, 15) keep their authored quest as step 1 and add a step 2 that sends it. Trails, parks and sports facilities keep one quest in a choice of sizes. Older completion records resolve their opportunity through the quest ID.

Invalid modes, sort options, and boolean strings return 400. The UI exposes these controls in Filters and offers individually removable active-filter chips. Reset restores relevance/any mode and clears visibility filters. Neutral fallback and general-task labels remain explicit; they are never described as exact matches in all mode.

### Profile situation and availability
`POST /profiles` accepts optional `context`, validated against `shared/user_context.json`. It contains `situation`, `country`, `state`, `city`, optional `school`, `travel`, `relocate`, `experience`, `availability`, `days`, `formats` (array), `budget`, and optional `transportation`. Text fields are limited to 120 characters. Empty selections mean no preference. Omitting `context` during later filter/profile saves preserves existing details; passing an empty object clears them. Details persist with the authenticated user profile and are editable in Profile.

Core discovery and broader recommendations apply saved context locally, before pagination:
- Available time limits the **suggested preparation quest**, not the full course/job duration (15/30/60-minute caps; 2+ hours has no upper cap). The UI cannot replace this suggestion with a step above that limit.
- Complete beginners/some experience exclude known intermediate/advanced requirements; intermediate excludes advanced. Unknown classifications remain possible and are not presented as verified eligibility. Explicit experience filters can narrow/override this preference.
- Formats use known online/in-person venues and explicit hybrid evidence. They combine with manual location constraints. Local-only plus a city excludes nonremote/hybrid items without matching city evidence.
- Free-only excludes paid/unknown cost. Until reliable paid amounts are available, Under $25/Under $100 conservatively show confirmed free records only, with a visible explanation.
- Preferred days constrain scheduled events with a known date (Pacific time); self-paced and undated records are not assigned invented weekdays.
- City/state/country/school and situation add small evidence-based ranking tie breaks (at most 0.49 points). They do not establish residency, student eligibility or work authorization. Travel time, transit access and relocation eligibility are not inferred; these fields are stored for later supported matching.

Feed responses expose `context_applied`, `context_notes`, per-card `context_reasons`, and `first_step_limit`. The UI offers an Edit link to the profile. These typed profile details are not added to Gemini prompts. Signed-in accounts have separate private profiles and activity.
